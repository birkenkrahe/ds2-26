- Why Google Colaboratory ("Colab")?
  #+begin_quote
  Use Colab for zero setup, free compute, easy sharing. Runs anywhere
  via browser, integrates naturally with Python (Jupyter
  notebook). Helps you focus on ideas rather than infrastructure but
  also teaches good notebook and literate programming skills.
  #+end_quote

- What is a Jupyter notebook?
  #+begin_quote
  Ju[lia]Py[thon]teR - pick one of these as runtime environment = now
  the notebook runs Julia, Python or R - all three work with SQL.

  You can use pretty much any other language using "magic" commands:
  they basically write the code as a file, and then you have to run it
  on the shell:

  ~%%writefile helloc~
  ...
  #+end_quote

- Why R?
  #+begin_quote
  R lets you focus on thinking with data rather than fighting the
  language. It’s built for analysis, exploration, and experimentation,
  and it makes it easy to see what your code is actually doing. In
  this course, we mostly use base R so you learn skills that transfer
  to other languages and tools.
  #+end_quote

- Why these topics?
  #+begin_quote
  These topics reflect how data science work really happens: you get
  data, clean it, process it, write functions to reuse your work, and
  speed things up when needed. The goal is not just to “get results,”
  but to write code that is clear, reusable, and efficient—skills
  you’ll use long after this course ends.
  #+end_quote

- What's missing/what to study next?
  #+begin_quote
  This course focuses on foundations, not every data science
  technique. Topics like machine learning, advanced modeling, large
  databases, and production systems come later. The goal is to prepare
  you to learn those topics faster and more critically once you
  encounter them.
  #+end_quote

- Why are we not using Python?
  #+begin_quote
  Python is widely used in data science, but learning data science is
  not the same as learning a popular language. In this course, R
  provides a clearer and more direct way to explore data, write
  analytical code, and understand performance trade-offs. Once you
  understand these ideas, picking up Python—or any other
  language—becomes much easier.
  #+end_quote

** DONE Review questions: Critiquing a plot

Q&A by ChatGPT (extracted exclusively from the [[https://docs.google.com/document/d/1iye6yXDJHQhBOfCebotwX2XmppeWf2wF7ZkRBY_ProY/edit?usp=drive_link][chart critique]])

1. What is the first thing you should evaluate when you see the title
   of a data visualization?
   #+begin_quote
   Whether the title states a neutral description of the data or
   already implies a conclusion or causal claim.
   #+end_quote

2. Why is it problematic if a plot compares only two groups when more
   categories could reasonably exist?
   #+begin_quote
   It can create a false dichotomy by excluding relevant groups, which
   biases interpretation toward a simplified narrative.
   #+end_quote

3. What questions should you ask about how categories such as “high”
   and “low” are defined?
   #+begin_quote
   You should ask what thresholds are used, whether they are relative
   or absolute, and how sensitive the results are to those choices.
   #+end_quote

4. Why does the absence of historical or contextual annotations matter
   in a time-series plot?
   #+begin_quote
   Without context, trends may be misinterpreted as structural changes
   rather than responses to external events like recessions or shocks.
   #+end_quote

5. How can axis scaling affect the viewer’s perception of differences
   between groups?
   #+begin_quote
   Truncated or narrow axes can visually exaggerate small numerical
   differences, making trends appear more dramatic than they are.
   #+end_quote

6. What is the risk of presenting aggregate data without
   distinguishing subgroups such as industries or sectors?
   #+begin_quote
   Aggregation can hide opposing trends within subgroups, leading to
   conclusions that do not hold at a more detailed level.
   #+end_quote

7. Why should visual differences always be compared to the underlying
   numerical differences?
   #+begin_quote
   Because visual impressions can be misleading, while numerical
   comparisons reveal whether differences are substantively large or
   small.
   #+end_quote

8. How should you approach uncertainty about the reliability of data
   sources used in a plot?
   #+begin_quote
   By separating concerns about data quality from concerns about how
   the data are selected, framed, and visualized.
   #+end_quote

9. What does it mean to say that a visualization is
   “narrative-driven”?
   #+begin_quote
   It means the visualization is designed to support a particular
   story or takeaway rather than to present a complete or neutral
   view.
   #+end_quote

10. Why is it important to consider which data are missing, not just
    which data are shown?
    #+begin_quote
    Because omitted data can change the interpretation entirely and
    may conceal the most important or informative patterns.
    #+end_quote

11. Why must observed correlations in a plot not be interpreted
    automatically as causal relationships?
    #+begin_quote
    Because correlation only shows that variables move together, not
    that one causes the other; external factors or reverse causality
    may be responsible.
    #+end_quote

** Review: Scoping and environment

1. What problem do *scoping rules* in R solve, and when do they become
   especially important?
   #+begin_quote
   Scoping rules determine how R stores and retrieves objects,
   especially when the same name exists in multiple places (e.g., a
   function argument, a global object, or a package function).
   #+end_quote

2. What is an *environment* in R or in Python, and how does it relate to
   memory and object lookup?
   #+begin_quote
   An environment is a virtual compartment that holds objects and
   functions and points to their memory location; R searches
   environments to resolve variable and function names.
   #+end_quote

3. What objects live in the *global environment*, and how can you
   inspect them?
   #+begin_quote
   All user-created or user-overwritten objects live in the global
   environment; they can be inspected with ~ls()~.
   #+end_quote

4. What happens when a function is called with respect to *local
   (lexical) environments* (also called a *scope*)?
   #+begin_quote
   Each function call creates a new local environment containing its
   arguments and locally created objects, which is discarded after the
   function finishes.
   #+end_quote

5. How does R’s *search path* work when resolving a function or variable
   name?
   #+begin_quote
   R searches environments in order, starting with ~.GlobalEnv~ and
   continuing through loaded packages until the object is found or the
   empty environment is reached.
   #+end_quote

** Review: Function arguments

1. What is meant by function argument matching in an expression like
   =f(args)=, for example with a function like ~plot~?
   #+begin_quote
   It refers to the process by which actual arguments supplied in a
   function call are matched to the formal parameters defined in the
   function. This can occur by *exact name*, *partial name*, *position*, or
   a *mixture* of these.
   #+end_quote

2. Define exact argument matching and state one advantage and one
   disadvantage.
   #+begin_quote
   Exact argument matching means that all argument names are written
   out in full and spelled correctly.  Advantage: It is safe and
   independent of argument order.  Disadvantage: It can be verbose and
   requires knowledge of the full, case-sensitive argument names.
   #+end_quote

3. Why does switching the order of arguments in a function call using
   exact matching (e.g., ~matrix~) still produce the same result?
   #+begin_quote
   Because each argument is identified by its full name, the function
   matches them by tag rather than by position, so order does not
   affect the result.
   #+end_quote

4. What is partial argument matching, and what condition must be
   satisfied for it to work correctly?
   #+begin_quote
   Partial argument matching uses abbreviated argument names.  It
   works only if the abbreviation uniquely identifies a single formal
   argument.
   #+end_quote

5. What can happen if a partial argument abbreviation is not unique
   (for example, using “d” instead of “da” for data)?
   #+begin_quote
   R may produce an error due to *ambiguity*, or it may match an
   unintended argument if multiple formal arguments begin with the
   same prefix.
   #+end_quote

6. Define positional argument matching and explain one risk associated
   with it.
   #+begin_quote
   Positional argument matching assigns arguments based solely on
   their order in the function call.  Risk: If the user does not know
   the exact order of formal parameters, arguments may be assigned
   incorrectly.
   #+end_quote

7. Where can you find the defined order of arguments for an R
   function?
   #+begin_quote
   In the =Usage= section of the function’s help file, or by using
   =args(function_name)= or printing the function name.
   #+end_quote

   #+begin_src R :session *R* :results output :exports both :noweb yes
     args(matrix)
   #+end_src

   #+RESULTS:
   : function (data = NA, nrow = 1, ncol = 1, byrow = FALSE, dimnames = NULL)
   : NULL

8. In a positional call to ~matrix()~, what happens if an intermediate
   argument such as ~byrow~ is omitted without naming later arguments?
   #+begin_quote
   Subsequent arguments shift position and may be matched to the wrong
   formal parameters, potentially producing unintended results or
   errors.
   #+end_quote

9. What is mixed argument matching? Provide a brief description.
   #+begin_quote
   Mixed argument matching combines different styles (exact, partial,
   and positional) within the same function call. This is common.
   #+end_quote

10. What is the role of ellipses (...) in a function definition?
    #+begin_quote
    Ellipses allow a function to accept any number and type of
    additional arguments, which can be passed on to other functions or
    handled internally.
    #+end_quote

** Review: ~apply~ functions so far (popquiz)

1. What is the main purpose of the *apply family* of functions in R?
   #+begin_quote
   They implement implicit looping by applying a function to elements
   or subsets of vectors, matrices, arrays, or lists, avoiding
   explicit ~for~ loops.
   #+end_quote

2. In the function ~apply(X, MARGIN, FUN)~, what does the argument
   ~MARGIN~ represent?
   #+begin_quote
   It specifies the dimension of the data structure to operate over: ~1~
   for rows, ~2~ for columns, ~3~ for layers in a 3-D array, and higher
   values for higher dimensions.
   #+end_quote

3. What is the difference between ~lapply~ and ~sapply~?
   #+begin_quote
   ~lapply~ always returns a list, while ~sapply~ attempts to simplify the
   result into a vector or matrix when possible.
   #+end_quote

4. What does the command ~apply(foo, 1, sum)~ compute if ~foo~ is a matrix?
   #+begin_quote
   It computes the sum of each row of the matrix ~foo~, because ~MARGIN =
   1~ indicates rows.
   #+end_quote

5. What problem does ~tapply~ solve and how are subsets defined?
   #+begin_quote
   ~tapply~ applies a function to subsets of a vector defined by
   categorical groups, typically using a ~factor~ variable to split the
   data.
   #+end_quote
